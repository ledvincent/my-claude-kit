# The workflow

## Where things live in a project

```
project-repo/
  CLAUDE.md                     rules Claude follows; points to openspec/ and okf/
  .claude/settings.json         enables dirox-kit, deny list, OpenSpec telemetry off
  .claude/commands/opsx/        generated by OpenSpec (/opsx:*)
  .claude/skills/openspec-*/    generated by OpenSpec; our commands call these
  openspec/
    config.yaml                 schema + the Dirox context and rules
    specs/<capability>/spec.md  current behaviour: requirements and scenarios
    changes/<change>/           work in progress: proposal, design, tasks, spec deltas, verification
    changes/archive/            done work, dated
  okf/
    index.md                    generated map, shown to Claude at session start
    log.md                      what changed, newest first
    domain/ decisions/          always present
    architecture/ data/ integrations/ runbooks/   added when needed
  .github/
    pull_request_template.md
    CODEOWNERS
    workflows/dirox-checks.yml  openspec validate + OKF validator
    scripts/okf-validate.mjs    copy of the kit's validator
```

**One fact, one place.** Behaviour (what the system does, its inputs, outputs and errors) goes in `openspec/`. Knowledge (what a term means, why we decided something, how the system is built and run) goes in `okf/`. They point to each other by path: a requirement ends with ``Knowledge: `okf/domain/order.md` ``.

**Names.** A Jira ticket `PROJ-123` gives the OpenSpec change `proj-123-<short-name>`, the branch `feature/PROJ-123-<short-name>` and one PR.

## The lifecycle

| Step | Command | Output |
|---|---|---|
| 1. Start | `/dirox-kit:start-change PROJ-123` | Ticket pulled, size confirmed, knowledge read, `openspec/changes/proj-123-…/` written by OpenSpec propose, review PR opened |
| 2. Review | people, in the PR | Approval (see sizes below) |
| 3. Build | `/dirox-kit:implement PROJ-123` | Approval checked, code and tests written by OpenSpec apply |
| 4. Verify | `/dirox-kit:verify PROJ-123` | `verification.md` in the change: each scenario and the test that proves it |
| 5. Close | `/dirox-kit:close-change PROJ-123` | OKF updated if needed, change archived into `openspec/specs/`, PR description |
| 6. Merge | people | CI green, PR reviewed and merged |

## Change sizes

`/dirox-kit:start-change` proposes the size; the person confirms it.

| Size | When | OpenSpec change | Review before code | Verify |
|---|---|---|---|---|
| Trivial | No change in behaviour: typo, config, dependency bump, refactor, a fix that restores specified behaviour | None | Normal PR review only | No |
| Normal | Everything else | Yes | Draft PR with the proposal; a BA or the Architect approves it in a PR review | Yes |
| Big | New module, data model change, new integration, or security (auth, permissions, personal data, secrets) | Yes | Separate proposal PR, approved by the BA and the Architect, merged before any code | Yes |

Approvals are always PR reviews by people. Claude checks them; it never approves, reviews or merges (the project's deny list blocks `gh pr review` and `gh pr merge`).

## Rules the kit adds to OpenSpec

They live in each project's `openspec/config.yaml`, which is OpenSpec's own way to add context and rules (no custom schema):

- `proposal.md` starts with `Jira: <KEY>` and `Size: <size>`; scenarios not yet in Jira are listed under "Not in Jira yet".
- Every Jira acceptance criterion becomes at least one scenario.
- Requirements cite the OKF concepts they rely on.
- Costly-to-reverse design decisions are marked "Decision record needed"; closing the change records them in `okf/decisions/`.
- `tasks.md` ends with a "Proof" group: one test per scenario, and the test name contains the scenario name.

## Knowledge (OKF)

- Claude sees only `okf/index.md` at session start (100 lines at most), and opens concepts when a task needs them.
- Knowledge is updated at `/dirox-kit:close-change`, in the same PR as the code, and only when the change is structural or adds knowledge.
- `index.md` files are generated by the validator from each concept's frontmatter. Nobody edits them by hand; CI fails if they are out of date.
- Concepts need `type` (set by their folder), `title`, `description` and `owner`. A person who checked a concept adds `verified: [{by: "human:<github-user>", at: YYYY-MM-DD}]`; Claude never writes it.
- Decisions are add-only: a new decision supersedes an old one, which becomes `status: deprecated`.

## CI

`.github/workflows/dirox-checks.yml` runs on every PR and on main:

- `npx @fission-ai/openspec@<pinned> validate --all --strict`
- `node .github/scripts/okf-validate.mjs okf`: errors for OKF conformance, a missing `owner` or a stale index; warnings for broken links.

## Existing projects

`/dirox-kit:setup-project` works on an existing repo and never overwrites what people wrote. Existing docs are not converted in one go: they move into `okf/` area by area, as tickets touch them (or at the kickoff of a takeover).
